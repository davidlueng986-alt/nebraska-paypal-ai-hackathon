## D-01 移除 AI 提交押金

狀態：已決定。押金機制整個移除，Nebraska 不再區分 AI 與人類的貢獻。

| 項目 | Before | After |
| --- | --- | --- |
| 押金 | agent 提交 PR 或漏洞報告時附 1 至 5 美元；有效則退回，標為垃圾則沒收 | 沒有 |
| 區分 AI 與人類貢獻 | 只有 AI 提交要付押金 | 不區分 |
| 裁決 | 72 小時裁決期；`nebraska:slop` 標籤觸發扣款；信譽好可減免押金 | 沒有 |
| Orders v2 用途 | `intent=AUTHORIZE`：押金的授權、扣款、取消授權 | `intent=CAPTURE`：緊急撥款（見 D-07） |
| MCP 工具 | `record_usage`、`budget_status`、`attach_stake` | `record_usage`、`budget_status` |
| 設定檔 | `.nebraska.yml` 的 stake 設定 | 刪除 |
| GitHub 整合 | GitHub App 在 PR 上顯示押金檢查項 | 只用於維護者認領 |
| 創新點 | 運行時計量、真錢付款、押金 | 運行時計量、真錢付款、有安全邊界的 AI 財務代理 |

理由：

- AI 已是開發過程的一部分，刻意區分人類與 AI 的貢獻沒有必要（你）。
- 押金可能阻礙真正有價值的貢獻，並帶來爭議（你）。
- 「怎樣可靠分辨 AI 與人手提交」本來就是未解決問題，規則無法執行。
- 沒收要裁決、申訴和仲裁者，等於另一個產品；被沒收的一方也可能在 PayPal 開爭議。
- 影片只剩一條主線。

留意：「提交成本近零、審查成本由維護者承擔」的不對稱仍然存在，只是押金不是對的工具。回應方式見 D-02。

## D-02 審查負擔改由收入回應

狀態：已決定。付款正好接上審查問題：維護者有了收入，就能用 AI 協助 review。

| 項目 | Before | After |
| --- | --- | --- |
| 審查負擔的解法 | 押金令垃圾提交有成本 | 收入令維護者有資源：有償的審查時間，加上 AI review 工具 |
| Nebraska 的 AI 角色 | 包括垃圾提交預篩：重現漏洞報告、跑測試、寫摘要 | 不做審查工具；維護者自選工具 |
| 敘事 | AI 欠兩筆帳，兩個機制各還一筆 | 一個機制直接處理「用了不付錢」，再經收入回應審查負擔；用閉環圖講 |

理由：兩個問題合成一條故事線，而且不用懲罰任何人。

留意：評審可能問「AI review 工具本身不貴」。真正的瓶頸是時間，所以要講清楚錢主要買的是維護者的時間，工具是次要的。

## D-03 搭便車問題的定位

狀態：部分決定。「Nebraska 無法單靠技術解決、也無法強迫企業付費」是你的判斷；下表的論點和變革路徑是 Claude 的建議。

| 項目 | Before | After |
| --- | --- | --- |
| 對搭便車的說法 | 沒有正面處理 | 明確承認無法強迫付款 |
| 「公司為甚麼要付」 | 供應鏈風險、Open Source Pledge 顯示有人願付、押金帶來信譽 | 願意付的人缺的是「付給誰、付多少」；付款方獨享供應鏈風險報告 |
| 論點 | — | 拿走兩個藉口：「不知道欠誰」和「太麻煩」 |
| 變革路徑 | — | 個人自願 → 公司預設開啟 → agent 平台預設開啟 |
| 定位句 | Nebraska 讓 AI 成為最大的付費者 | 不聲稱解決集體行動困境，改講可見度和管道 |

理由：

- 誠實承認邊界，比過度承諾更有說服力。
- 集體行動困境有已知的槓桿：令搭便車可見（Ostrom 強調的監察）、降低付款成本、給付款者獨享的好處（Olson 的選擇性誘因）。
- AI 令使用集中到少數平台，決策者變少。Olson 指出小群體比大群體容易提供公共財。

## D-04 敘事語言與標語

狀態：部分決定。「共同責任」類的官方用語保留但少用，是你的決定；新標語是 Claude 的建議。

| 項目 | Before | After |
| --- | --- | --- |
| 主標語 | AI 是開源史上最大的使用者，Nebraska 讓它成為最大的付費者。 | AI 是第一個確切知道自己欠了誰的開源使用者。 |
| 安全標語 | 錢怎樣動由確定性程式碼決定，LLM 只負責理解、核實和解釋。 | AI 決定錢去哪裡；程式碼決定錢永遠不能去哪裡。 |
| 搭便車標語 | — | 付不付仍由你決定，但「不知道」從今天起不再是藉口。 |
| 「共同責任」類用語 | 未定 | 保留，只在 Devpost 描述結尾用一次 |
| 「一小步、一大步」類說法 | 考慮中 | 不用 |

理由：

- 「最大」沒有數據支持；「最大的付費者」是承諾不了的結果。
- 新主標語的張力來自真實的反差：AI 切斷了維護者的回報渠道，卻是第一個能精確記帳的使用者。
- 「一小步」等於主動承認影響小，而潛在影響是評分準則之一。
- 「共同責任」屬官方客套話，有必要出現但沒有感染力（你）。

## D-05 AI 在授權內決定與發起交易

狀態：已決定。AI 不只做分析，而是直接決定金額和發起交易；怎樣保證安全見 D-06。

| 項目 | Before | After |
| --- | --- | --- |
| 原則 | LLM 不碰金額；AI 只負責理解、核實和解釋 | 安全由程式碼保證，公平由 AI 決定 |
| AI 對金額的影響 | 只輸出標籤或限定範圍的數值 | 決定 c 和 n，直接改變金額 |
| AI 可發起的動作 | 回報用量 | 暫緩收款人、發起每月 Payouts、提出緊急撥款、處理未領取和失敗的款項 |
| 組件 | — | 新增月結代理（Treasurer），每個動錢工具都經規則閘 |

理由：

- 比賽問的是把 AI 放上駕駛座會怎樣，特別獎也設有 Best Use of Agentic Commerce。
- 只做分析的話，和單純用 AI 分析供應鏈風險沒有分別（你）。

留意：對評審的理由不應該是「AI 夠強」。基準測試量度能力，不量度抗操縱能力；而 Nebraska 的收款人正是 AI 輸入的撰寫者。

## D-06 安全設計

狀態：建議・待確認。你說過安全設計由你負責；這一版是 Claude 的建議，供你修改。

| 項目 | Before | After |
| --- | --- | --- |
| 安全原則 | 四條：LLM 不碰金額、外部內容當數據、每個動作可重算、預算是硬上限 | 三層分工（事實、判斷、守門）加不變量 I1 至 I7 |
| 外部內容 | 一律當作數據 | 只有決策層讀；月結代理只看類型化結果；問題目錄固定 |
| AI 輸出 | 固定格式標籤或限定範圍數值 | 類型化問題（Jev 或結構化輸出 LLM），帶信心值；信心不足用保守預設值 |
| 人類授權 | 預算上限 | PayPal 訂閱數量即預算；改預算和撥款都要在 PayPal 頁面重新同意 |
| 可分配的錢 | 當月預算 | 已實際收到的預算，以 `PAYMENT.SALE.COMPLETED` 為準 |
| 收款人風險 | 新認領設冷靜期 | 冷靜期加 `payee_risk`，門檻刻意偏低 |
| 框架 | — | PayPal 團隊的三條問題：人類授權了沒有、此刻在範圍內嗎、事後能證明嗎 |

理由：假設 AI 會被騙，然後限制被騙的後果。最壞情況是已驗證的維護者之間分錯錢，總額和單一套件都有上限。用 PayPal 自己的框架，對 PayPal 的評審最有說服力。

## D-07 超出授權的動作經 PayPal 批准

狀態：建議・待確認。AI 可以提出超出授權的動作，但批准只能由付款方在 PayPal 頁面作出。

| 項目 | Before | After |
| --- | --- | --- |
| 超出授權的動作 | 沒有這個概念 | 由 AI 建立 Orders v2 訂單，付款方在 PayPal 頁面批准後才執行 |
| 例子 | — | 關鍵依賴出現安全公告後的緊急撥款，金額 100、250 或 500 美元 |
| AI 可否自行批准 | — | 不可以 |
| 批准後何時發放 | — | 記入維護者帳上，隨當期批次發放 |

理由：給「人類授權了沒有」一個 AI 偽造不了的證據；影片也多了一個「AI 提議、人類批准」的場景。

留意：「緊急」撥款要等到當期批次才發放。如要即時發放，需要另設撥款批次的編號規則，並修改 I4。

## D-08 PayPal API 組合

狀態：建議・待確認。從 D-01 和 D-07 推導而來，端點已對照 PayPal 文件。

| 用途 | Before | After |
| --- | --- | --- |
| 收預算 | Subscriptions，端點未核實 | Subscriptions 數量制計劃：每單位 1 美元，數量即預算；改預算用 revise，須付款方重新同意 |
| Orders v2 | `intent=AUTHORIZE`：押金 | `intent=CAPTURE`：緊急撥款 |
| 付款 | Payouts | Payouts，不變 |
| 對帳 | Webhooks，事件名稱未定 | Webhooks，事件已列明；加 `PAYMENT.SALE.COMPLETED` 作可分配金額的依據 |
| PayPal AI Toolkit | agent 經 MCP 建立訂閱、查交易、產生報表 | 月結代理只用唯讀的交易報表作交叉核對 |
| 押金裁決期 | 72 小時，對應授權的 3 天 honor period | 刪除 |

理由：數量制計劃令「人類授權」有 PayPal 原生的證據；只分配已收到的錢，避免付出未入帳的預算。

## D-09 用量維持確定性，AI 只調權重

狀態：建議・待確認。用量是付款方的帳單，由程式碼計算；AI 只影響 c 和 n。

| 項目 | Before | After |
| --- | --- | --- |
| 用量歸因 | AI 判斷哪些套件是實質使用、哪些只是順帶安裝 | 程式碼按訊號和去重規則計算，AI 不能修改 |
| AI 的影響點 | 用量分類和 n | c 和 n |
| 用量單位 | 直接依賴計 1，間接依賴按層數遞減 | u = 本月用到該套件的 repo 數，每個 repo 按最淺深度乘 γ 的 d 次方，γ = 0.5 |

理由：帳單必須可重算、可審計；把 AI 放在權重上，「事實由程式碼、判斷由 AI」的分工更清楚。

## D-11 分配規則具體化

狀態：建議・待確認。實作需要確定的數值；全部是起始值，沒有實證依據。

| 規則 | Before | After |
| --- | --- | --- |
| 單一套件上限 | 套件多時設上限，例如 25% | max(25%, 2/K)，K 為有權重的套件數；超出部分按權重重新分配 |
| 最低發放額 | 未滿 10 美元滾存 | 按維護者跨付款方的合計計算，未滿 10 美元滾存 |
| 未認領款項 | 超過期限按公式重新分配 | 6 個月後回流到該付款方下月的預算池 |
| 冷靜期 | 新認領設冷靜期 | 新認領或更改 PayPal 電郵後 14 天 |
| 多位維護者 | 交由專案自行決定 | 預設平均分，專案可自訂 |
| AI 信心不足 | — | c 和 n 退回 1.0 |
| 算例 | 純用量對比 Nebraska 兩種情況 | 加入「AI 關閉」：C 由 23 美元到 69 美元，再到 161 美元 |

理由：上限用 max(25%, 2/K)，套件少時不會扣得太緊；算例加入「AI 關閉」，是為了證明 AI 的判斷本身改變了多少錢。
